今回のローカルbuildも同じ結果。本番公開インデックスは33件ある。

各検証の結果・対象件数・欠落を保持し、成果物の未生成も報告する。

P1-3: 既存記事生成Actionに承認なし公開経路がある
根拠: .github/workflows/generate-content.yml は手動起動のみだが、OpenAI APIを使用し、
content:auto-publishの後にgit commit / git pushする。

人の医学的承認なしにstatus=published / noindex=falseに書き換える。
参照URLが存在することは科学的妥当性の確認と同じではない。
対応: 集客システムからこのActionを呼ばない。別PRで下書き提案と人の承認を必須化し、
有料生成は明示承認時のみ。Phase 1では既存Actionの変更・実行はしていない。

P2-1: 流入ページ別の診断開始・完了への帰属が不足
根拠: collectGa4Weekはページ、自然検索ランディング、記事→診断イベントを取得するが、
buildWeeklyReportは記事一覧への結合が中心で、全ランディング別の開始・完了を保持しない。
DBの開始・完了は全体集計であり、自然検索から来た同一集団の完了数ではない。
保存snapshotのtop_articlesは上位10件に限定され、過去の全ページ候補抽出には不足する。
対応: 既存GA4取得にlandingPagePlusQueryString × eventNameのセッション指標を追加検証。
Organic Searchセグメントの開始・完了を同じ定義で取得し、全体DB件数とは明確に分ける。
非加算のsessions/usersをページやイベント間で足し合わせない。
まずGA4の既存ディメンションで実現し、診断ロジック・DBスキーマ変更を避ける。

P2-2: 「Google自然検索流入」の名称と取得条件が一致していない
根拠: collectGa4WeekはsessionDefaultChannelGroup=Organic Searchのみ。
他の検索エンジンも含み得る一方、dashboard-model.jsのカード名はGoogle自然検索流入。
対応: ユーザー要件どおり「自然検索流入」に名称を統一する。
Google限定指標が必要な場合はGoogleのsource条件を追加し、GSCクリック数と同一視しない。

P2-3: データ状態と診断可能性の改善
既存はmissing_configuration / error / real / fixtureを分け、GSC空応答を需要0としない。
一方sourceError()がAPI失敗をapi_request_failedへ集約し、403、期限切れ、429、timeoutを区別しない。
取得日時も主にレポート全体のgenerated_atで、取得元ごとの成功時刻・試行時刻が不足。
GSCで他ページのデータがあると未返却ページを0へ補完する箇所があるが、
Search Analyticsは上位行制約があるため「未返却」と「実測0」は分離が必要。
対応: 秘密を含めないエラー分類、source別attempted_at / fetched_at / data_through、
no_rows / delayed / partial / unavailableを追加。ソース全体realだけでページの0を確定しない。

P2-4: 改善候補A～Eと週次上位3件の選定が未実装
技術監査と内部リンク検査はあるが、週次実績と統合した優先順位付けはない。

データ不足時には3件を無理に埋めず、不足・接続要件を出す。
